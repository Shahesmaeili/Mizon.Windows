## Request and implementation

Upgrade every Windows .NET project to .NET 11, preserving existing UI, native
integration, consent and playback behavior. Target Windows platform versions,
minimum supported OS versions and Windows App SDK packages are unchanged.

All 16 existing C# projects now target `net11.0` with their existing Windows suffix.
The six direct ASP.NET Core/Extensions 10.0.14 package references are aligned to
11.0.0. `global.json` selects SDK 11.0.100 with patch-only roll-forward. Runtime
fixture paths and current executable examples follow the new TFM; historical
task notes remain historical.

A fresh Visual Studio MSBuild rebuild reproduced an SDK 11 `GenerateClsidMap`
`MissingMethodException` binding `HostModel` metadata types. The same project
builds through the .NET CLI. ExplorerCommands now imports the SDK explicitly and
overrides only its three COM-generation tasks to use the supported .NET TaskHost
under full-framework MSBuild. The SDK's tasks and output format remain unchanged;
there is no custom COM generator, nested build, SDK patch or registration change.
A clean VS Rebuild verifies the fix independently of warmed COM output.

Reference: [Microsoft's .NET TaskHost configuration](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-10/sdk#configure-net-tasks).

The new independent `Mcp/Mizon.Windows.PerformanceBenchmarks` console project
links actual deep-link production code and references production MCP contracts.
It measures route parsing/canonicalization and source-generated JSON/framing on
synthetic data. It does not expose a new MCP operation or alter product behavior.
The .NET 10 executable and complete dependencies were preserved and then rebuilt
with installed SDK 10.0.400-preview.0.26322.102 in an isolated external project,
linking the unchanged production files with the same contracts assembly boundary.
The .NET 11 candidate uses SDK 11.0.100. Timing runs are serialized by the integration
owner to avoid cross-agent benchmark/build interference.
